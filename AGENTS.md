# LEXIS engineering rules

- The owner's full-product contract v2 supersedes the first-slice endpoint. The target is all M01–M14, X01–X10, FLOW-01–FLOW-10 and horizontal requirements; implement S0–S9 as compatible, independently verified journeys. Do not stop at a plan, disconnected screens, ports, mocks or a previous green build. When a live dependency is unavailable, complete its independent contracts/tests/UI and continue other work, while keeping the exact remaining gate visible.
- Read the current remote HEAD before changes; `c39997bc243f54af5c1ae5045ebfc1c51058fa85` is the v2 entry baseline, not permission to ignore later work. Prefer a review branch/PR, small commits and no force push. Preserve source snapshots and historical verification.
- Keep every v2 requirement, acceptance story, risk and stage in `docs/REQUIREMENTS_TRACEABILITY.md`. Claims use `specified`, `implemented-local`, `contract-tested`, `configured`, `verified-live`, `release-verified` or an explicit awaiting/blocked state. A checkpoint records HEAD, completed IDs, commands/results, blockers and the next concrete action; a count of pages/tests is not product completion.
- Start with `START_HERE_CODEX.md`, `docs/DECISIONS_AND_SOURCE_OF_TRUTH.md`, `docs/architecture.md`, `docs/product.md` and `docs/implementation-plan.md`; use `docs/source/` for the complete original product contract. Preserve the warm graphite/espresso/sand, strongly fogged matte-glass direction. Exact tokens and pixels remain unapproved; readability takes priority.
- Source precedence is latest explicit owner instruction > approved decisions > product specification > reference images > implementation. The lightweight handoff has five curated WebP references plus an overview; thirteen historical images were deliberately excluded. Read applicable source text and open the real relevant images before visual changes; never claim unseen material was reviewed.
- Treat `references/2026-10-22-light/` and `docs/source/` as provenance snapshots. Never replace responsive UI with reference screenshots or ship raw reference images as app UI/background assets. Do not copy fictional metrics, tiny text, bright backgrounds behind reading, rejected purple/neon/noir/orbital experiments or unsupported affordances from mockups.
- Build one complete, verifiable learning flow at a time. Do not add placeholder controls that imply working integrations.
- Use strict TypeScript. Keep pure learning rules in `src/domain`, use cases in `src/application`, provider/storage implementations in `src/infrastructure`, reusable UI in `src/components`, and routes in `src/app`. Domain code must not depend on React, Next.js or storage SDKs.
- Knowledge belongs to a user + meaning + skill, never to a word alone. Saving a meaning is not evidence of mastery. Keep evidence, scheduling and estimates distinct. Never increase speaking or writing estimates from a recognition exercise.
- Preserve the approved fourteen-module strategy, Knowledge Flow, contextual Quick/Panel/Dedicated/Persistent levels, Smart Inbox and learner control. Do not implement all modules at once. FSRS is the approved scheduling direction; current `heuristic-v1` is an explicit temporary algorithm and must never be reported as FSRS or calibrated mastery.
- AI/voice/dictionary integrations must implement provider-neutral ports. Explain estimates, record provenance and version, and allow disputed evidence to be excluded/replayed. Never claim an integration works without a real connection and verification.
- Browser storage is a local single-device mode, not authentication or cloud backup. Handle invalid persisted state, storage denial and write failure visibly. Do not store raw audio or private imported books by default.
- Preserve existing learning data v1 through a validated, versioned migration with backup/preview and stable legacy ID mapping; do not freeze the product to five legacy skills. Keep Reader appearance preferences separate from evidence; undo may reverse a fresh save only when doing so preserves all existing evidence. Local session orchestration belongs in application, with injected clock/IDs and a storage port; React provides bindings, not a second set of learning rules.
- Preserve unreadable persisted bytes and block writes until recovery or an explicitly confirmed reset. Validate the source/skill relationship and canonical replay order, including equal timestamps. Tab stale-state guards are best effort, not database transactions.
- Keep secrets server-side. Do not put secret/service-role keys in `NEXT_PUBLIC_*`. Treat database RLS as mandatory; test ownership isolation and cross-user foreign keys. Do not run remote migrations or publish externally without user authorization.
- Use versioned, checked-in SQL migrations. Make learning writes atomic and retry-safe before introducing remote persistence. Keep backups, retention and deletion behavior explicit.
- Mobile first, including iPhone safe areas and Safari. Use semantic controls, accessible names, visible keyboard focus, dialog focus management, sufficient contrast and `prefers-reduced-motion`. Avoid animated blur, large backdrop-filter layers and unnecessary WebGL.
- Voice previews must label every simulated state and never imply active capture, transcription, synthesis or pronunciation scoring. Use a soft layered membrane and quiet motion; no noisy orbital graph. ASR confidence is never a pronunciation grade.
- Real Voice, when configured, has a separate permission/capture/processing/playback lifecycle. Stop/exit/pointer cancellation/background interruptions release tracks and cancel stale audio. PTT does not prove live transport; ASR/TTS do not prove a specialized pronunciation scorer. Record consent/data flow and test each capability separately.
- Saving/importing/revealing/accepting AI corrections never proves independent competence. Keep assistance, modality, context, task/rubric/provider version and event identity explicit. Challenge excludes disputed influence immediately and replays all dependent schedules/projections/recommendations; archive/unsave must not purge evidence. Explicit permanent deletion is separate and covers derived data/cache/memory.
- Use one shared clock mechanism for due/day-sensitive UI, including scheduled boundaries, focus, visibility and data synchronization. UTC facts and local presentation/day limits are separate; test background returns, wrong clocks and timezone boundaries.
- Existing consent permits publishing project source/documentation to `tupomark/Eng`. It does not authorize paid plans/API costs, destructive production migrations or public disclosure of private learner materials. Never request already applicable consent again; first complete concrete reviewable independent work.
- Use deterministic domain tests for scheduling and evidence; database tests for constraints and access control; Playwright for the first full learning journey, persistence and mobile layouts. Run typecheck, relevant tests and production build before handoff. Record checks that could not be run.
- Pin dependency versions and commit the lockfile. Use actual documented APIs. Keep external adapters optional and disabled until configured.
- Changes should be small and independently reviewable. Do not rewrite unrelated work or change the agreed visual direction silently. Document working features, prototypes and outstanding production gates separately.
- After each meaningful milestone update `docs/PROGRESS.md` and requirements traceability with actual changed files, dated test results, real screenshots when available, limitations and next steps. Preserve historical verification; never present earlier counts as a fresh run. Record decision changes with date, initiator, rationale and impact. Linear work is conditional on verified tool/workspace availability.
